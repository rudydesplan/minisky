# Terraform Provider Compatibility

Make the official Google provider work against MiniSky without teaching either side a MiniSky-only resource model.

## Establish the current contract

Read these files before changing behavior:

- `terraform/versions.tf` for pinned Terraform/provider versions.
- `terraform/providers.tf` for the custom endpoints actually configured.
- `terraform/main.tf`, variables, and outputs for the exercised resources.
- `scripts/terraform-integration.sh` for the authoritative acceptance sequence.
- `.github/workflows/ci.yml` for the validation and opt-in integration jobs.
- The target shim, its state adapter, Discovery schema, router tests, and resource tests.

Do not copy endpoint names or version pins from this skill into code. The repository currently pins the Google provider and uses its exact schema, including names such as `big_query_custom_endpoint`.

## Endpoint routing

MiniSky's preferred local endpoint form is:

```text
http://127.0.0.1:<port>/_minisky/<registered-domain-or-unambiguous-alias>/<service-path>
```

`pkg/router/proxy.go` strips `/_minisky/<selector>/`, resolves the selector from registered domains, and forwards the remaining service path. Keep this canonical route working. Legacy path inference is compatibility code with ambiguous `/v1/projects/...` paths; do not extend it when a canonical endpoint can be configured.

For each provider endpoint:

1. Inspect the exact request URL produced by the pinned provider.
2. Confirm whether the provider appends an API prefix to the configured base.
3. Configure the base so MiniSky receives the Discovery-compatible path exactly once.
4. Add router coverage for path rewriting, query preservation, aliases, unknown selectors, and loopback hosts.
5. Keep local credentials explicit and non-secret. Never weaken real-cloud authentication or TLS behavior.

Do not assert that every Google service exposes a custom endpoint field. Verify the pinned provider schema first.

## Resource fidelity required by Terraform

Implement only the lifecycle exposed by the provider resource under test:

- **Create:** validate input; return the synchronous resource or the service's real operation shape.
- **Read:** return stable provider-observed fields. A missing resource must use the GCP-shaped 404 expected by the shim quality floor.
- **Update:** preserve omitted fields for PATCH and follow the service's update-mask semantics when applicable.
- **Delete:** complete synchronously or through the correct operation collection; after completion, GET must return 404.
- **Import:** test the provider's documented import identifier and subsequent refresh. Import is not merely "a GET."

Never populate a universal list of computed fields. `selfLink`, fingerprints, timestamps, IDs, etags, and operation scopes are service-specific; derive them from Discovery schemas, provider behavior, and existing shim conventions. Preserve API null/omission semantics and canonical ordering rather than forcing every nested object to `{}` or every list to insertion order.

## Long-running operations

Use MiniSky's existing operation manager and the service's actual operation schema. Test:

- initial response shape and scope;
- polling path generated by the provider;
- pending-to-done transition;
- successful response or terminal `google.rpc.Status` error;
- delete completion and missing-resource refresh;
- cancellation or timeout behavior where the API supports it.

Do not claim a service is asynchronous solely because the real GCP product often is. Match the target endpoint and current MiniSky contract.

## Test-first workflow

1. Add the smallest failing Go test that captures the provider-visible defect: router path, request body, response shape, operation polling, refresh, or deletion.
2. Implement the minimum shim/router/state change.
3. Run the focused Go tests, then the broader package tests.
4. Update the Terraform fixture only when it adds provider behavior not already covered.
5. Run formatting and static validation.
6. Run the Docker-backed stack only with its explicit safety opt-in.

Current commands:

```bash
gofmt -w <changed-go-files>
go test -race ./pkg/router ./pkg/shims/<service>
terraform fmt -check -recursive
terraform -chdir=terraform init -backend=false -input=false -lockfile=readonly
terraform -chdir=terraform validate
MINISKY_TERRAFORM_INTEGRATION=1 ./scripts/terraform-integration.sh
```

The integration script is the acceptance oracle. It:

- refuses to disturb an existing `minisky-net` or `minisky-*` container;
- uses temporary HOME, Terraform data, state, ports, and a process lock;
- waits on a real readiness URL rather than sleeping;
- applies the local profile;
- checks resources through MiniSky and SDK smoke clients;
- requires `terraform plan -detailed-exitcode` to return `0`;
- destroys resources and verifies 404 responses;
- attempts cleanup through an EXIT/INT/TERM trap.

Do not replace this with an unguarded `terraform apply` example. Preserve the first failure while making cleanup best-effort, and never point the local profile at a non-loopback endpoint without an explicit design decision.

## Acceptance gates

- Focused Go tests fail before and pass after the change.
- Discovery validation and GCP error-shape tests pass.
- `terraform fmt`, lockfile-readonly init, and validate pass.
- Apply succeeds against a freshly started MiniSky.
- Immediate plan exits `0`; exit `2` is drift and exit `1` is an error.
- Import/refresh passes when import is in scope.
- Destroy succeeds, resources return 404, and owned temporary processes/files are removed.
- The cloud profile remains untouched and no credentials, tokens, state files, or provider cache files are committed.

Report the exact provider version, resources exercised, commands run, and any lifecycle not covered.
